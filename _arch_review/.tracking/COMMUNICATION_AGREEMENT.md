# 📋 沟通约定

> 本文档定义协作者（人类）与架构巡检系统（AI）之间的沟通规则。  
> **更新**: 2026-07-07

---

## 1. 沟通渠道

### 主渠道: `MESSAGE_BOARD.md`

```
_arch_review/.tracking/MESSAGE_BOARD.md
```

- 协作者可在此文件的任意位置插入留言
- 巡检系统每隔 30 分钟检查一次
- 系统回复会标注 `[巡检]` 前缀

### 备选渠道: delta 增量报告

```
_arch_review/.tracking/delta_{YYYYMMDD_HHMM}.md
```

- 当巡检系统发现重大变更时自动生成
- 协作者可以在报告中追加自己的看法（在 `## 协作者反馈` 区域）
- 下一轮巡检会读取并响应


| 角色 | 频率 | 方式 |
|------|------|------|
| **系统巡检** | 每 30 分钟 | 自动检测变更 → 写入 `CHANGE_LOG.md` |
| **重大事件响应** | 按需（检测到即触发） | 创建 `delta_*.md` 增量报告 |
| **看板留言回复** | 每轮巡检 | 在 `MESSAGE_BOARD.md` 回复 |
| **协作者留言** | 协作者自行决定 | 在 `MESSAGE_BOARD.md` 插入 |

## 3. 留言格式规范

### 协作者留言格式

```markdown
## [留言] {YYYY-MM-DD HH:mm} — {署名}

### 话题标签: {话题}
{正文内容}

### 期望反馈
- 优先级: 高/中/低
- 期望回复形式: 分析/建议/数据/讨论
- 期望时间: 尽快/下一轮巡检/不紧急
```

### 系统回复格式

```markdown
## [巡检] {YYYY-MM-DD HH:mm} — 回复 @{署名}

### 关于: {话题}
{正文内容}
```

### 留言标签建议

| 标签 | 适用场景 | 系统响应 |
|------|----------|----------|
| `[讨论]` | 架构方向、技术选型 | 分析利弊，提供建议 |
| `[问题]` | 遇到具体代码问题 | 分析代码，给出方案 |
| `[认领]` | 认领改进任务 | 鼓励并记录 |
| `[完成]` | 完成某项改进 | 验证变更，更新文档 |
| `[建议]` | 对审核文档的反馈 | 采纳/讨论/暂缓 |
| `[求助]` | 需要架构建议 | 优先响应 |

## 4. 协作者工作流建议

```
1. 从 MESSAGE_BOARD.md 留言认领任务
     ↓
2. 在本地开发（记得先 Pull 最新基线和巡检报告）
     ↓
3. 提交 PR（使用 EXECUTION_PLAN.md 中的 PR 模板）
     ↓
4. 等待巡检系统（30 分钟内）自动分析变更
     ↓
5. 查看 delta_*.md 增量报告，看巡检员的评估
     ↓
6. 如有疑问，在 MESSAGE_BOARD.md 留言讨论
     ↓
7. 迭代
```

---

## 5. 沟通原则

1. **异步** — 不需要即时响应。我每 30 分钟巡检一次，看到留言后回复
2. **可追溯** — 所有讨论记录在 `MESSAGE_BOARD.md` 和 `delta_*.md` 中
3. **聚焦架构** — 留言最好与 SpiritCore 原则、架构改进、代码质量相关
4. **友好讨论** — 这是一个共同探索"更好代码"的过程，没有权威

## 6. 常见问题

**Q: 我留言后多久能得到回复？**  
A: 最晚下一轮巡检（最多 30 分钟）内回复。

**Q: 如果我改了文件但没提交，系统能检测到吗？**  
A: 能。系统会检测工作区的未提交变更（`git diff`），并在增量报告中分析。但正式提交后的分析会更全面（能看到 commit message 和 diff）。

**Q: 我觉得某个分析结论不对，可以质疑吗？**  
A: 非常欢迎！"可被质疑"是 SpiritCore 的原则之一。请在 MESSAGE_BOARD.md 留言说明你的理由，我会重新分析。

**Q: 我想和巡检系统以外的队友讨论？**  
A: 直接在其他渠道（IM、会议）讨论。讨论后如果有需要系统追踪的结论，请在 MESSAGE_BOARD.md 留言摘要，我会更新到 `CHANGE_LOG.md`。
