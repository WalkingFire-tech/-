# 真谛：大规模一致性改造的五步法

> 来源：2026-07-08 core/ DB 迁移实践总结
> 提炼自同伴在迁移 30 个文件时的思维方式分析

## 核心真谛

**在进行任何需要大规模一致性改造的工程任务时，按以下五步执行：**

### 第一步：先建立模式再执行

不要直接开始改代码。先从已有代码（或已完成的同类改造）中提取标准操作步骤，形成一份清晰的"迁移模式清单"。这个清单本身就是从现成代码中提取的模式总结，而不是凭空想象出来的。

> 对应种子真谛 **T2**：先确定如何解决再解决

### 第二步：识别约束边界

理解代码"做了什么"而非"看起来做了什么"。明确：

- 哪些操作可以保留（如 `conn.commit()`）
- 哪些需要移除（如 `conn.close()`）
- 哪些有隐含行为需要注意（如 `with sqlite3.connect(...) as conn:` 的事务管理 vs 连接关闭的语义）

> 对应种子真谛 **T7**：悖论本质是定义边界问题

### 第三步：分类批量处理

按复杂度或特征对任务分组，而非逐一处理。

```
1 个调用的文件 → 简单（批量处理）
2 个调用的文件 → 中等（批量处理）
特殊模式文件 → 单独处理（如包含 _db() 方法的复杂结构）
```

这种分类使处理流程更高效，也降低了出错概率。

> 对应种子真谛 **T3**：多方案并行概率最优

### 第四步：保持一致性验证

反复确认"已迁移文件的模式"，确保新代码延续已有的惯例，不凭直觉创造新的实现方式。维护大型代码库时，**一致性比局部最优更重要**。

> 对应种子真谛 **T1**：诚实罗列分歧优于强行融合  
> 不一致就是分歧。如果新代码与已存在代码风格不一致，需要明确理由。

### 第五步：风险前置评估

在执行前识别潜在的语义变化或边界情况，而不是等出了问题再排查。具体做法：

- 问"迁移后这个行为会变吗？"
- 识别隐式依赖（如 `with` 语句结束后是否回滚未提交的事务）
- 制定应对策略（如果隐式行为变了，需要额外处理什么）

> 对应元宪法 **R1**：未经沙盒验证的真谛视同毒药  
> 迁移模式在执行前就需要被"沙盒验证"——在小范围测试中确认其行为符合预期。

## 等级评估

| 维度 | 评估 | 说明 |
|------|------|------|
| **跨域普适** | ✅ | 适用于代码迁移、架构重构、数据清理、配置变更等任何大规模一致性改造任务 |
| **逻辑自洽** | ✅ | 五步之间存在自然的因果顺序：先知道做什么、再知道边界在哪、再分组执行、再验证一致、再确认安全 |
| **认知降熵** | ✅ | 将模糊的"改代码"任务化为结构化的五步流程，减少决策疲劳和遗忘 |
| **反脆弱性** | ✅ | 越在不同类型的改造中被使用，步骤越完善。每次应用都是一次验证和优化 |

**等级建议：L3 → 待升级到 L4**（经过 3 次以上不同类型的大规模改造验证后可升级）

## 使用场景举例

| 场景 | 适用性 |
|------|--------|
| 数据库访问层统一重构 | ✅ 本真谛的来源场景 |
| API 接口协议升级 | ✅ 需要建立"新旧协议映射模式" |
| 日志系统统一替换 | ✅ 需要分类处理不同日志使用模式 |
| 配置文件格式迁移 | ✅ 需要风险前置评估隐式行为变化 |
| UI 组件库统一升级 | ✅ 需要保持一致性验证 |
