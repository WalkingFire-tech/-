# Claude Code 协作五原则：从技巧焦虑到高效共生

**来源**：ferlich 基于大半年 Claude Code 使用经验总结
**核心观点**：技巧永远学不完，底层原则只有几条；把 Claude 当作需要不断改善协作方式的**团队成员**，而非用完即放的工具

---

## 原则一：把上下文当内存管理

上下文窗口使用率超过 **40%** 时，Claude 开始变笨；超过 **60%** 时，会选择性漏掉指令。上下文不会突然崩溃，而是像**内存泄漏**一样慢慢变笨。

**实践方法**：
- 上下文使用率达到 **50%** 时手动执行 `/compact`
- 长任务主动拆分为多段，**每段新开一个会话**
- 切换任务前让 Claude 写**交接总结**
- 开多个终端/会话，**每个会话只装一件事**

**衍生技巧**：
- 回退比纠正更有效：走偏了按 `Esc Esc` 回滚，别在已污染的上下文里修修补补
- 子代理的价值在上下文隔离：将噪音留在子代理中，只把结论带回主会话
- CLAUDE.md 控制在 60 行以内——这是一张**上下文预算表**，不是文档库

---

## 原则二：给 Claude 一个验证自己工作的办法

Claude Code 创建者 Boris 认为最重要的建议是：**让 Claude 自己检查自己的工作**。加上这个闭环后，产出质量能翻两三倍。

**对比**：
- 传统方式：Claude 写代码 → 人手动跑 → 人检查 → 人描述偏差 → Claude 修改（4-5 轮）
- 自验证方式：Claude 写代码 → 自己跑测试 → 自己对比结果 → 自己改（1-2 轮）

**适用边界**：验证条件**天然清晰**的任务效果极佳；验证条件**本身模糊**的任务，人的判断仍不可替代。

---

## 原则三：并行不是多开窗口

真正的并行是**把任务拆成相互独立的单元**。三个会话干三件相互独立的事：读代码的不写代码，写代码的不审查自己写的代码，审查的不受前面任何上下文影响。

---

## 原则四：规则是长出来的，不是写出来的

CLAUDE.md 的配置体系应该**从实际错误中生长**，而非一次性预设所有规则。

**进化历程**：V1(498行)→V5(发现200行后规则被忽略)→V10(90行，只记真犯过的错)→V18(.claude/rules/拆分)→V25(Gotchas最有价值)→V30(47行)

**关键教训**：
- CLAUDE.md 不是文档，是**上下文预算表**
- 规则价值与精确程度成正比
- Gotchas 最值得维护——每条背后都是真实踩过的坑
- 别用 CLAUDE.md 代替 Code Review

---

## 原则五：简单任务别上重武器

| 档位 | 任务规模 | 做法 |
|------|----------|------|
| 第一档 | 5分钟以内 | 直接说需求，不用Plan Mode |
| 第二档 | 半小时到几小时 | 先Plan Mode讨论方案，再Normal Mode执行 |
| 第三档 | 跨天跨模块 | 上工作流，用Subagent拆分，Worktree并行 |

**规则**：如果做之前不确定大概要多久，直接升一档。

## 对联盟拓荒者的启发

1. **上下文管理**→系统的分层记忆和经验池需要控制注入量，避免上下文污染
2. **自验证闭环**→阶段5自我验证 + 代码执行沙箱 = 自验证能力
3. **并行独立性**→9路径并行需要确保路径间不互相污染
4. **规则生长**→Gotchas机制可映射为"经验池中的失败教训"
5. **任务分级**→CognitiveDispatcher的意图分类 = 任务分级
