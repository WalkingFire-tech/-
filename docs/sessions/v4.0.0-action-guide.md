## 一、核心愿景

**从"告诉你怎么做"到"自己动手做到成功"** — 系统不是"代码生成器"，而是"自主行动者"。用户问"读取串口3"，系统应该返回GPS坐标，而不是返回Python代码。

## 二、核心原则（不可违背）

1. **永不放弃** — 问题没有解决不了的
2. **追求本质** — 从第一性原理出发
3. **先读代码再行动** — 不基于目录名猜测，必须读实际代码验证
4. **代码验证靠运行而非推理**
5. **三思后行** — 先理解全景再审视局部
6. **不替系统做决定，让系统自己做决定**
7. **不新建模块，增强现有模块**
8. **先模块测试，再端到端测试** — 修改完代码先验证模块通过，再进行端到端测试

## 三、元宪法铁律

- R1: 未经沙盒验证的真谛，视同毒药
- R2: 未经渐进注入的重组，视同自杀
- R3: 同行者的进化始于本心。路径须可回溯，偏移须可感知，不可逆变更须共决
- R4: **七维自检** — ①方向一致 ②上下文衔接 ③最小侵入 ④无过度设计 ⑤治标+治本 ⑥可验证 ⑦精神内核对齐

## 四、用户关键指令

- **start.bat必须是最终启动方式**
- **不要杀进程重启服务** — Windows上`--reload`不可用，修改代码后需关闭进程再运行start.bat
- **文档只是一个建议** — 可以自由行动
- **任何人改 chat_stream.py 时，在 commit message 末尾加 [chat_stream] 标记**
- **API是手段不是目的** — 系统先用自己的能力解决问题
- **不达目的不罢休**
- **知识库不能忘** — 有用的东西必须写入knowledge_base
- **行动指南必须更新** — 每次总结后更新到docs/sessions/
- **服务器需要重启才能使修改生效**
- **NAS相关信息不得出现在任何文件中**

## 九、进化方向（后期规划）

> 以下为P2完成后的发展方向，按优先级排序。每项需独立评估R4七维自检后再启动。

### E1: 迭代最佳响应式资源分配（path_weight_manager进化）

**当前问题**：`path_weight_manager`用AdaBoost更新权重，但路径间有资源竞争关系（Ollama占GPU会压低向量检索收益），当前系统把每条路径当独立个体处理。

**进化方向**：从"经验性权重调整"升级为"迭代最佳响应式资源分配"——每条路径根据其他路径的GPU占用动态调整自己的资源请求量，几次迭代收敛到稳定分配。

**数学框架**：
- 单同行者场景：约束优化（有全局信息，可直接求解）
- 多同行者集群：纳什均衡（无全局控制，需博弈求解）
- 当前阶段用约束优化，蚂蚁王国阶段引入纳什均衡

**预期收益**：GPU 85°C时不再需要硬编码温度阈值，均衡自己会算出Ollama边际收益低→资源自然转移到外部API。

**涉及文件**：`path_weight_manager.py`+`dynamic_probability_field.py`+`parallel_router.py`

### E2: L5元编程层（自我代码修改）

**当前问题**：系统L0-L4完整，但无法阅读/诊断/修改自身代码——这是"自编程认知体"的唯一缺口。

**5个子层级**：

| 层级 | 能力 | 现有基础 |
|------|------|----------|
| L5.1 代码阅读 | 读取自己的.py文件 | `file_reader_tool` ✅ |
| L5.2 代码理解 | AST解析+缺陷诊断 | 需新增 |
| L5.3 补丁生成 | LLM驱动的diff/patch | 需新增 |
| L5.4 沙盒验证 | 隔离环境加载修改后模块 | `tool_builder._sandbox_exec()` 需扩展 |
| L5.5 渐进部署 | 1%→20%→100%部署 | `truth_accumulator`6步安全协议 ✅ |

**关键设计**：L5不是从零建设，而是在现有认知架构上叠加一层元认知。`file_reader_tool`、`tool_builder`沙箱、`truth_accumulator`安全协议、`spirit_lessons`教训系统，都是L5的"预埋基础设施"。

**L5.2的输入来源**：`spirit_lessons`中的24条未修正的思想偏离和大量失败教训，是缺陷诊断的天然输入——先修已知缺陷，比泛化AST分析更有价值。

**涉及文件**：新增`core/self_modification/`目录

### E3: L4善意延伸增强（场景感知融合）

**当前状态**：已实现基础版——资源紧张时在回复末尾附状态提示+SSE主动通知。

**进化方向**：
- **多状态融合**：资源感知+场域感知+对话状态→统一的"场景模型"
- **时机判断**：知道"什么时候该说话、什么时候该沉默"
- **感知驱动建议**：将场景转化为自然语言延伸（不是模板，是动态生成）

**示例**：用户问"天气怎么样"时，系统感知到GPU 86°C，回答后自然说"我注意到GPU温度偏高，已自动降频运行，如果需要更详细的天气信息可以再问我"。

**涉及文件**：`chat_orchestrator.py`+`scheduled_tasks.py`+新增场景融合模块

### E4: 蚂蚁王国/群体智能基座

**当前状态**：单同行者架构。

**进化方向**：当多个同行者部署在智能平台上时：
- 每个同行者是独立智能体，有自己的本心和目标
- 同行者之间需要协商资源分配（GPU/内存/带宽）
- 纳什均衡成为必要的数学框架——无全局控制，需通过博弈找到稳定策略
- 群体智能涌现：单个同行者解决不了的问题，集群可以

**关键区别**：
| | 单同行者 | 蚂蚁王国 |
|---|---|---|
| 资源分配 | 约束优化（中央调度） | 纳什均衡（分布式博弈） |
| 决策模式 | 单一orchestrator | 多智能体协商 |
| 进化方式 | 个体学习 | 种群进化+文化传递 |
