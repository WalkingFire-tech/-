## 一、核心愿景

**从"替系统修工具"到"让系统学会造工具"** — 系统不应该按照既定的东西去执行，而是学会掌握解决问题的方法，然后不断优化这种解决问题方法的能力。工具应该是系统临时造的，而不是开发者修改的。

## 二、核心原则（不可违背）

1. **永不放弃** — 问题没有解决不了的，只有想不想得到方法
2. **追求本质** — 从第一性原理出发
3. **先规划，再更新行动指南，然后按步骤执行**
4. **代码验证靠运行而非推理**
5. **三思后行** — 先理解全景再审视局部，先搜索既有讨论再行动，先根因思考再修复
6. **不再替系统做决定，而是让系统自己做决定** — 不替系统修工具，让系统自己修；不替系统加约束，让系统自己学

## 三、元宪法铁律

- R1: 未经沙盒验证的真谛，视同毒药
- R2: 未经渐进注入的重组，视同自杀
- R3: 未经人类允许的进化，视同背叛
- R4: **七维自检** — 行动前必须通过：①方向一致 ②看板衔接 ③最小侵入 ④无过度设计 ⑤治标+治本 ⑥可验证 ⑦精神内核对齐

## 四、行动前自检流程（R4强制）

每次修改代码或提出方案前，必须完成：

1. **理解全景** — 架构、哲学、看板历史、路线图阶段，不盯着局部
2. **搜索既有讨论** — 看板/路线图/架构分析，不重新发明轮子
3. **根因思考** — 问题是孤立故障还是未落地的架构原则？
4. **标本兼治** — 热修复(P0)与架构方案分离
5. **七维自检** — 全部通过才行动
6. **最优判断** — 依赖链排序，不做的事也明确列出

## 五、用户关键指令

- **start.bat必须是最终启动方式** — 每次修改完毕后确保start.bat可用
- **不要杀进程重启服务** — Windows上`--reload`不可用，需手动重启
- **文档只是一个建议** — 可以自由行动，按最稳妥最优的方式执行
- **任何人改 chat_stream.py 时，在 commit message 末尾加 [chat_stream] 标记**
- **文档是实时更新的** — 每次执行前必须重新读取PHASE2_ARCHITECTURE.md和留言板
- **API是手段不是目的** — 系统先用自己的能力解决问题，API只是补充
- **不达目的不罢休** — 在未达到用户真正目的之前，不接受半成品输出
- **知识库不能忘** — 有用的东西必须写入knowledge_base
- **行动指南必须更新** — 每次总结后更新行动指南到docs/sessions/
- **不照搬外部代码** — 按七维自检提取真正新价值，避免与已有实现重复
- **不要新建模块，用现有模块增强** — 新概念应融入现有模块，而非创建新目录
- **服务器需要重启才能使修改生效**

#### 7.5.1 infrastructure/ _get_conn()全面迁移

**问题**：infrastructure/下188处`db._get_conn()`裸cursor调用，绕过DatabaseManager的线程安全锁和重试机制，且手动`conn.commit()`容易遗漏。

**解决方案**：全部迁移到DatabaseManager高级API：
- 写操作: `conn=db._get_conn()+conn.execute()+conn.commit()` → `db.execute(commit=True)`
- 读多行: `conn=db._get_conn()+cursor.fetchall()` → `db.query()`
- 读单行: `cursor.fetchone()` → `db.query_one()`
- DDL批量: 多个`conn.execute()` → `db.executescript()`

**结果**：188处→6处，37个文件受益。

后续扩展：core/(430处85文件)+backend/(4处3文件)全部迁移，全项目622->6处。
路径同步修复3处(experience_pool.db/tool_cache.db缺data/前缀)，缺失导入1处，语法错误1处。

#### 7.5.2 closed_loop_orchestrator状态机修复

- `_phase_accumulation`: `_get_conn()`裸cursor迁移到`db.execute(commit=True)`
- `_check_protection`: 迭代上限时走ACCUMULATION(有结果)或PROTECTION(无结果)，而非返回False不保护
- `_phase_metacognition`: 异常后显式设`state=METACOGNITION`确保状态机正确转移

#### 7.5.3 CognitivePlanner渐进式接入Phase1

**背景**：chat_orchestrator手动调用CognitivePlanner的私有方法（`_perceive`, `_learn`等），散布在7个阶段中。`process()`从未被调用。

**Phase 1方案**：在阶段7（反思学习）中，异步运行`cp.process()`做完整L1-L6认知循环（15秒超时），旁路结果与主管道信号交叉验证：
- 高紧迫度信号补充（主管道未捕获时告警）
- 校验失败交叉检测（旁路发现校验问题但主管道通过时记录）
- 情绪信号补充（旁路捕获到情绪但主管道未捕获时记录）
- 旁路内省报告融合到L6内省层
- 完全降级安全：process()失败不影响任何现有逻辑

**后续Phase 2/3**：逐步将手动调用替代为process()结果，最终process()成为主路由。
