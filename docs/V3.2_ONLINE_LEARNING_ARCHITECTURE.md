## 一、架构总览

### 核心理念

**从被动等待到主动学习，从离线批处理到在线增量学习，从固定参数到递归优化**

```
用户对话 → 实时检测 → 即时学习 → 递归优化
    ↓
    ├─ 语义漂移 → 标记需澄清
    ├─ 隐式否定 → 标记低质量
    ├─ 用户修正 → 即时生成规则
    └─ 负面情绪 → 触发归纳
    
每周 → 元归纳器 → 优化学习参数
```

## 三、核心模块详解

### 3.1 对话流学习器

**文件**: `infrastructure/dialogue_stream_learner.py`

**职责**: 实时监听对话，检测隐式学习信号

#### 检测器架构

```python
class SemanticShiftDetector:
    """语义漂移检测 - 用户重复提问但换说法"""
    - 相似度计算: 词重叠率
    - 阈值: 0.7
    - 触发: 标记需澄清

class ImplicitNegationDetector:
    """隐式否定检测 - 从措辞识别不满"""
    - 检测模式:
      * 不太对、还是不对
      * 没.*理解、没.*明白
      * 不准确、不自然
      * 处理不了
      * 你.*不懂、你.*不明白
    - 触发: 标记低质量 (quality_score=20)

class EmotionAnalyzer:
    """情绪分析 - 推断用户满意度"""
    - 关键词权重:
      * 负面: 沮丧(0.5)、失望(0.5)、不对(0.3)
      * 正面: 满意(0.3)、谢谢(0.4)、棒(0.4)
    - 输出: {negative, neutral, positive}
    - 触发: 连续3次负面 → 强制归纳

class CorrectionDetector:
    """修正检测 - 捕捉用户纠正"""
    - 检测模式:
      * "不对，应该是..."
      * "你记错了，实际是..."
      * "其实正确答案是..."
    - 触发: 即时生成规则 (无需等待归纳周期)
```

#### 事件流

```
intent_parsed ──→ _on_intent_parsed()
                       ↓
                   _analyze_user_input()
                       ↓
                   检测学习信号
                       ↓
                   learning_opportunity事件

plan_executed ──→ _on_plan_executed()
                       ↓
                   记录系统响应
```

### 3.2 元归纳器

**文件**: `meta/meta_induction.py`

**职责**: 分析规则效果，递归优化学习策略

#### 参数优化逻辑

```python
当前参数:
  min_support: 3          # 模式最小支持度
  min_confidence: 0.7     # 规则最小置信度
  quality_threshold: 50   # 质量阈值

优化策略:
  规则成功率 < 0.6:
    → 降低规则优先级
    → 提高置信度阈值 (减少低质量规则)
  
  规则成功率 > 0.8:
    → 提高规则优先级
    → 降低置信度阈值 (增加规则覆盖)
  
  规则总数 < 10:
    → 降低支持度阈值 (生成更多规则)
  
  规则总数 > 50:
    → 提高支持度阈值 (减少冗余规则)
```

#### 持久化

```yaml
# config/induction_params.yaml
min_support: 3
min_confidence: 0.7
quality_threshold: 50
max_rules_per_run: 10
rule_types:
  prefer_model:
    enabled: true
    priority: 5
  reroute:
    enabled: true
    priority: 6
meta:
  optimization_interval_days: 7
  success_rate_threshold: 0.6
  adjustment_factor: 0.1
```

## 四、数据流架构

### 4.1 学习机会数据流

```
用户输入
    ↓
IntentParser.parse()
    ↓
发布 intent_parsed 事件
    ↓
DialogueStreamLearner._on_intent_parsed()
    ↓
检测器分析:
    ├─ SemanticShiftDetector.detect()
    ├─ ImplicitNegationDetector.detect()
    ├─ EmotionAnalyzer.analyze()
    └─ CorrectionDetector.detect()
    ↓
发现学习信号
    ↓
处理学习机会:
    ├─ 隐式否定 → 标记低质量 → experience_pool.db
    ├─ 用户修正 → 生成规则 → learning_rules.db
    └─ 连续负面 → 触发归纳
    ↓
发布 learning_opportunity 事件
    ↓
Planner._on_learning_opportunity()
    ↓
触发即时归纳 (可选)
```

### 4.2 元归纳数据流

```
定期触发 (每7天)
    ↓
MetaInductor.optimize_parameters()
    ↓
analyze_rule_performance()
    ↓
查询 learning_rules.db:
    SELECT action, COUNT(*), AVG(success_rate)
    FROM learning_rules
    WHERE status='active' AND apply_count > 0
    GROUP BY action
    ↓
计算各类规则成功率
    ↓
调整参数:
    ├─ 成功率低 → 降低优先级、提高阈值
    ├─ 成功率高 → 提高优先级、降低阈值
    ├─ 规则少 → 降低支持度
    └─ 规则多 → 提高支持度
    ↓
保存到 config/induction_params.yaml
    ↓
下次归纳使用新参数
```

## 五、关键技术决策

### 5.1 为什么选择模块化检测器？

**决策**: 4个独立检测器类 vs 内嵌逻辑

**理由**:
1. ✅ 职责单一 - 每个检测器专注一种信号
2. ✅ 易于扩展 - 添加新检测器无需修改主类
3. ✅ 可独立测试 - 单元测试更简单
4. ✅ 可复用 - 检测器可在其他场景使用

### 5.2 为什么需要元归纳器？

**决策**: 递归优化学习策略

**理由**:
1. ✅ 自我完善 - 系统学会如何学习
2. ✅ 适应性强 - 根据实际效果调整参数
3. ✅ 避免过拟合 - 动态平衡规则数量
4. ✅ 递归深度 - 可被更高阶归纳器优化

### 5.3 为什么即时生成规则？

**决策**: 检测到修正立即生成 vs 等待归纳周期

**理由**:
1. ✅ 实时响应 - 用户修正立即生效
2. ✅ 提升体验 - 无需等待24小时
3. ✅ 捕捉时机 - 用户反馈最及时
4. ✅ 减少遗忘 - 避免修正信号丢失

## 七、与V3.1的差异

### V3.1 (之前)

```
用户对话 → 经验池 → (等待24小时) → 归纳总结 → 规则库
                ↓
          需要显式反馈 (👍👎)
```

### V3.2 (现在)

```
用户对话 → 实时检测 → 即时学习
    ↓
    ├─ 语义漂移 → 标记需澄清
    ├─ 隐式否定 → 标记低质量
    ├─ 用户修正 → 即时生成规则
    └─ 负面情绪 → 触发归纳
    
每周 → 元归纳器 → 优化学习参数
```

### 关键差异

| 维度 | V3.1 | V3.2 |
|------|------|------|
| 学习模式 | 被动等待 | 主动实时 |
| 反馈依赖 | 需要显式 | 隐式信号 |
| 规则生成 | 离线批处理 | 在线即时 |
| 参数优化 | 固定 | 递归动态 |
| 元认知 | 无 | 完整支持 |

1. **增强情绪分析**

3. **多模态学习**
